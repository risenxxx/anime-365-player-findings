# Предлагаемые решения

Для каждой подтверждённой проблемы: что происходит, почему так ведёт себя текущий код и как
это можно исправить в исходниках. Как проблемы воспроизводились и что показали логи —
в [REPORT.md](REPORT.md).

Здесь два вида кода, и их важно различать:

- **Патчи** [`patches/01…07`](patches/README.md) — минимальные правки поверх текущего
  кода. Они **проверены на стенде** теми же сценариями: до и после.
- **Эскизы** в этом документе — то, как может выглядеть исправление в исходниках
  (явное состояние, лестница ретраев и т. д.). **На стенде они не прогонялись.** Это
  направление, а не готовый код. Перед выкаткой их стоит прогнать теми же сценариями
  (`node runner/run.mjs --patched=…`).

Все наблюдения сделаны в Chrome 155 на macOS. Пороги (секунды, число попыток) подобраны
для стенда, на проде их стоит выбирать по телеметрии сайта (`videoTelemetry` уже
содержит `err`, `rb`, `lm`).

## Статус на 27.10.2026: что уже сделано на сайте и что осталось

Код сайта после исправлений (`concatenate?1793007100`, `embed?1793007100`, `swMain.js?v=27`)
проверен теми же сценариями. Подробности и цифры — в
[REPORT.md](REPORT.md#проверка-после-исправлений-сайта-27102026).

**Сделано и подтверждено:** H3 (синтетического ответа нет, negative cache, перемотка
работает), H4 (свежие ссылки по 403), H6b (SW спрашивает режим у вкладки), H8 (тайм‑аут
чтения 15 с в SW, сторожевой таймер 30 с в плеере), `cache: 'no-store'` в запросах SW,
позиция при ошибке больше не сбрасывается в 0:00 (H2).

**Осталось:**
1. **Новое — лестница повторов слишком быстро уходит на паузу 30 с** (раздел
   [ниже](#новое-лестница-повторов-слишком-быстро-уходит-на-паузу-30-с)). Это регрессия:
   короткий отказ CDN теперь может дать 30 с простоя.
2. **H2 — битое место не перешагивается:** при порче байтов на CDN ошибка декодирования
   повторяется на одной позиции (5–7 раз). Решение — восстанавливаться на 2–5 с дальше
   ([H2](#h2-прыжок-в-начало-серии-после-ошибки), пункт 5).
3. **H5 — нет сверки версии файла:** после подмены файла под тем же `m` первое открытие
   всё ещё даёт одну ошибку декодирования (кэш удаляется уже после неё). Решение — валидатор
   `ETag`/`Last-Modified` в метаданных ([H5](#h5-битый-кэш-живёт-сутки), патч 03).
4. **H8 без SW:** сторожевой таймер плеера срабатывает через 30 с; можно сократить до
   10–15 с, как в SW.
5. **О сетевых сбоях сайт узнаёт только из телеметрии** (`recovery_*` в
   `videoTelemetry`): `notifyBroken` теперь вызывается лишь после 3 ошибок декодирования.
   Если на сервере есть отчёты по `brokenVideo`, сетевые сбои в них больше не попадут.

## Общий контекст: как Chrome и SW обрабатывают сбои

Это определяет, какие решения работают:

1. **Медиастек Chrome сам повторяет запрос после сетевого обрыва** (около 30 попыток с
   растущей паузой 0.3–0.8 с). А HTTP‑ошибка (например, 503) на повторе для него
   **фатальна** — сразу `MEDIA_ERR_NETWORK`.
2. **SW отвечает 206 до того, как узнал статус CDN.** Поэтому любой отказ CDN браузер
   видит как обрыв тела ответа и повторяет. Короткие сбои с SW незаметны. Долгие,
   наоборот, растягиваются: 403 повторяется десятки раз, прежде чем плеер узнаёт об ошибке.

Отсюда два правила для решений ниже: **не отдавать браузеру сырую HTTP‑ошибку, если её
можно пережить повтором**, и **не повторять то, что повтор не лечит** (403, битые байты).

## H1. Бесконечный цикл перезагрузок

**Что происходит.** При повторяющемся сбое плеер бесконечно делает `load()` → видео
начинает играть → снова ошибка. `notifyBroken` не вызывается никогда.

**Почему.** `concatenate:67-71`: счётчик ошибок обнуляется по первому `playing` после
перезагрузки. Порог «больше 4 ошибок подряд» недостижим, если видео каждый раз успевает
заиграть.

**Что показал патч 01** (окно «5 ошибок за 2 минуты»): цикл ограничен, `notifyBroken`
вызывается. Но после пятой ошибки плеер просто встаёт, и пользователь видит **меньше**
видео, чем с багом (112 с против 142 с). Значит, мало остановить цикл: нужно решить, что
делать дальше.

**Предлагаемое решение — лестница эскалации:**

1. **Обнулять счётчик по реальному прогрессу, а не по `playing`.** `playing` приходит сразу
   после `load()`, даже если через секунду снова будет ошибка. Сброс — только после,
   например, 30 с устойчивой игры.
2. **Повторять по ступеням с нарастающей паузой и случайным разбросом (jitter):**
   1. перезагрузить тот же источник (0.5 → 1 → 2 с);
   2. обновить подписанные ссылки через `/sources/` (заодно закрывает H4);
   3. переключиться на `data-alternative-sources`;
   4. `notifyBroken` + сообщение пользователю с кнопкой «Повторить», и продолжать фоновые
      попытки раз в 30–60 с, пока вкладка видима.
3. **Не тратить попытки без сети:** при `navigator.onLine === false` ждать события `online`.
4. **Слать в телеметрию каждую ступень.** Тогда будет видно, сколько просмотров спасает
   каждая.

Эскиз (не проверен на стенде):

```js
const RETRY = {
  steps: ['reload', 'reload', 'refreshSources', 'alternative', 'broken'],
  stableMs: 30000,        // столько устойчивой игры обнуляет лестницу
};
let step = 0, stableTimer = null;

player.on('timeupdate', () => {
  if (stableTimer || step === 0) return;
  stableTimer = setTimeout(() => { step = 0; stableTimer = null; }, RETRY.stableMs);
});
player.on('error', async () => {
  clearTimeout(stableTimer); stableTimer = null;
  if (!navigator.onLine) await new Promise(r => window.addEventListener('online', r, { once: true }));
  const action = RETRY.steps[Math.min(step, RETRY.steps.length - 1)];
  const delay = Math.min(500 * 2 ** step, 8000) * (0.75 + Math.random() / 2);
  step++;
  telemetry('retry', { action, step, code: player.error()?.code });
  setTimeout(() => recover(action), delay);   // recover() всегда восстанавливает позицию, см. H2
});
```

**Как проверить:** `h1-cut503-nosw`, `h1-outage-nosw`, `h1-long-outage-sw`. Критерий:
цикл ограничен, и при этом сыграно не меньше, чем без исправления.

## H2. Прыжок в начало серии после ошибки

**Что происходит.** После ошибки в середине серии видео начинается с 0:00 и встаёт на
паузу. Два пути:
- **H2a:** первая ошибка случилась ровно при `ct = 0` (на практике — без контроллера SW:
  первый визит, неудачная регистрация, браузер без SW). Позиция `0` «залипает», и
  следующая ошибка позицию уже не восстанавливает.
- **H2b:** ошибка декодирования (code 3/4) при активном SW уходит в ветку blacklist, где
  восстановление позиции не подключено вообще.

**Почему.** Одна переменная `lastSuccessTime` одновременно хранит позицию и служит
флагом «надо восстановить» (`concatenate:67`, `:72-74`). А путей перезагрузки несколько
(`load()`, blacklist, смена источника), и каждый восстанавливает позицию по‑своему или
не восстанавливает.

**Что показал патч 01:** в начало больше не бросает. Но если байты испорчены на самом CDN,
восстановление ведёт ровно на то же место, и ошибка повторяется (4–6 раз → `notifyBroken`).

**Предлагаемое решение — позиция как явное состояние:**

1. **Хранить последнюю хорошую позицию отдельно** и обновлять её по `timeupdate`, только
   при нормальной игре: не во время перемотки, не во время восстановления,
   `readyState ≥ 3`. Ноль и позиция сразу после `load()` её не затирают.
2. **Записывать её в `sessionStorage`** с ключом по id перевода. Тогда и перезагрузка
   страницы или iframe (включая `location.reload()` из `initWaitUntilEmbedAvailable`)
   вернёт пользователя на место.
3. **Одна функция `recover()` для всех путей перезагрузки:** обычный `load()`, blacklist,
   смена источника, обновление ссылок.
4. **Перематывать по `loadedmetadata`, а не по `canplay`.** `play()` вызывать, только если
   видео играло до ошибки.
5. **Перешагивать испорченное место:** если ошибка декодирования повторилась в пределах
   ±1 с от прошлой, восстанавливаться на 2–5 с дальше (примерно один GOP). После
   нескольких таких шагов — `notifyBroken`.
6. **Перематывать через `player.currentTime()`, а не через элемент:** это учитывает
   смещения частей в `concatenate` (`currentVideoStart`).

Эскиз (не проверен на стенде):

```js
const key = 'pos:' + player.el().dataset.id;
let goodPos = +sessionStorage.getItem(key) || 0, restoring = false, lastFailPos = -1;

player.on('timeupdate', () => {
  const t = player.currentTime();
  if (restoring || player.seeking() || player.readyState() < 3 || t < 0.5) return;
  goodPos = t;
  sessionStorage.setItem(key, t.toFixed(1));
});

function recover(action) {
  const wasPlaying = !player.paused() || player.error();
  let target = goodPos;
  if (player.error()?.code === 3) {                       // MEDIA_ERR_DECODE
    if (Math.abs(target - lastFailPos) < 1) target += 3;  // то же место → перешагнуть
    lastFailPos = target;
  }
  restoring = true;
  player.one('loadedmetadata', () => {
    if (target > 0) player.currentTime(target);
    player.one('seeked', () => { restoring = false; if (wasPlaying) player.play(); });
  });
  doReload(action);   // reload / blacklist + &rand / refreshSources / alternative
}
```

**Как проверить:** `h2a-no-sw-support`, `h2b-decode-sw`, `h5-twin-sw`. Критерий: позиция не
уходит в 0, а на испорченном месте проигрывание продолжается дальше.

## H3. SW выдумывает ответ, когда не знает размер файла

**Что происходит.** Если размер файла узнать не удалось (CDN ответил 5xx, CORS‑ошибка, нет
доступного `Content-Range`), SW отвечает синтетическим `206 bytes 0-104857600/*`. Конец
придуман (100 МБ, к тому же на 1 байт больше), а размер неизвестен (`*`). Видимый эффект —
ошибка на старте и проигрывание без кэша, если CDN не открывает `Content-Range` в
`Access-Control-Expose-Headers`.

**Почему.** `swMain.js:1660-1695` `_ensureMeta` глотает любое исключение и возвращает
`null`. Fetch‑обработчик (`:2640-2737`) откатывается на прямой запрос только при
исключении, а на `null` выдумывает ответ.

**Что показали патчи:** первая версия патча 02 честно отдавала `fetch(request)`, и это
оказалось **хуже**: браузер получал прямой 503, а он для медиастека фатален (ошибка на
старте там, где без патча её не было). Текущая версия сначала дважды повторяет метаданные.
Ошибок нет, но старт на 2–4 с дольше. А если заголовок недоступен постоянно, каждый
запрос заново тратит ~1.5 с на повторы.

**Предлагаемое решение:**

1. **Повторять и сам прямой путь.** `fetch(request)` с 2–3 попытками; браузеру вернуть
   первый успешный ответ CDN — настоящий 206 с настоящими заголовками. Ошибку отдавать
   только после всех попыток. 403/404 не повторять.
2. **Запоминать неудачи (negative cache).** Если для `m` метаданных нет, помнить это минут
   5. Следующие запросы сразу идут прямым путём, без задержки на повторы.
3. **Никогда не придумывать конец файла.** Если размер неизвестен, синтетического ответа
   нет вообще. Константа на 100 МБ и ошибка на единицу исчезают сами.
4. **Ловить кривые конфиги CDN.** Если на 206 нет читаемого `Content-Range`, слать в
   телеметрию событие с хостом (например, `sw_no_meta`). Сервер или edge, который забыл
   `Expose-Headers`, станет виден сразу, а не по жалобам. Сейчас на проде заголовок
   открыт (проверено живой записью), так что это страховка.

Эскиз (не проверен на стенде):

```js
const noMeta = new Map();                    // m -> until (ms)
async function directWithRetry(request, tries = 3) {
  let last;
  for (let i = 0; i < tries; i++) {
    try {
      const r = await fetch(request);
      if (r.ok) return r;                    // настоящий 206 от CDN
      last = r;
      if (r.status < 500 && r.status !== 429) break;   // 403/404 повтор не лечит
    } catch (e) { last = e; }
    await new Promise(res => setTimeout(res, 400 * 2 ** i));
  }
  if (last instanceof Response) return last;
  throw last;
}

// в fetch-обработчике:
if ((noMeta.get(mParam) || 0) > Date.now()) return event.respondWith(directWithRetry(request));
event.respondWith((async () => {
  const meta = await ensureMetaWithRetry(mParam, start, url);   // 2 попытки
  if (!meta?.totalSize) {
    noMeta.set(mParam, Date.now() + 5 * 60e3);
    report('sw_no_meta', { host: hostAlias(url) });
    return directWithRetry(request);
  }
  return new Response(serve(...), { status: 206, headers: realHeaders(meta, start, end) });
})());
```

**Как проверить:** `h3-first-503-sw`, `h3-hidden-range-sw`. Критерий: нет ошибки на старте,
старт не медленнее, чем без исправления, нет повторной задержки на каждом запросе.

## Остальные проблемы

Для них патчи уже дали нужный результат на стенде. В исходниках решение может выглядеть
так же.

### H4. Истёкшая подпись ссылки

**Что происходит.** После истечения подписи около 1.5 минут ожидания, затем цикл ошибок,
сотни запросов к CDN с 403. Свежие ссылки плеер не запрашивает.

**Решение** (патчи 02, 04, 05 — **проверено**: 0 ошибок, 0 с простоя):
- **SW:** на ответ CDN 403/410 сообщать странице `{type: 'originStatus', status}` сразу,
  не дожидаясь, пока кончится буфер. 403 не повторять: повтор той же ссылки его не лечит.
- **Плеер:** по этому сообщению вызывать уже существующий `_refreshSources()` и
  переключать `src` на свежую ссылку с сохранением позиции.
- **Отказы 5xx/429 при переоткрытии соединения:** несколько повторов с паузой в `serve()`,
  прежде чем рвать поток.

### H5. Битый кэш живёт сутки

**Что происходит.** Если под тем же `m` оказался другой файл (перекодирование, другой CDN),
куски из кэша смешиваются с новыми байтами, и при каждом открытии — ошибка декодирования
и серия с начала.

**Решение** (патч 03 — **проверено**: 0 ошибок, 0 сбросов):
- хранить в метаданных кэша валидатор (`ETag`, иначе `Last-Modified`; оба на проде открыты
  в `Expose-Headers`) и сверять его с CDN раз за жизнь экземпляра SW;
- при расхождении — удалить кэш `m`;
- на сообщение `blacklist` тоже удалять кэш `m`, а не только останавливать загрузчик.

### H8. Зависший поток CDN

**Что происходит.** CDN перестаёт отдавать байты, но соединение не закрывает. Плеер стоит
без ошибки, пока пользователь не перемотает далеко. Небольшая перемотка не помогает.

**Решение** (патч 06 — **проверено с SW**: 0 с простоя вместо 114 с):
- таймаут чтения в `serve()`: 12 с без байтов от CDN → оборвать соединение и переоткрыть
  с той же позиции;
- без SW у Chrome своего таймаута нет. Там нужен сторожевой таймер в плеере на долгий
  `waiting` при непустой сети (эскиз, не проверен).

### H6b. После перезапуска SW кэширование молча выключается

**Что происходит.** Браузер останавливает простаивающий SW (на живом сайте — через ~45 с
паузы). Новый экземпляр начинает с выключенным кэшированием, и после продолжения уже
закэшированная серия качается заново. Пользователь этого не видит, но это лишний трафик
CDN.

**Решение** (патч 07 — **проверено**: обхода кэша нет):
- сохранять выбранный страницей режим (`setVideoCachingEnabled`, `setVideoMode`) в Cache
  Storage;
- новый экземпляр восстанавливает его до обработки первого запроса.

### Двойное хранение и блокировка HTTP-кэша

**Что происходит.** SW скачивает серию обычным `fetch()`, и Chrome дублирует её в HTTP‑кэш
(в тестовом профиле — 249 МБ поверх 617 МБ в Cache Storage). На живом CDN второй
параллельный range‑запрос к тому же файлу упал с `ERR_CACHE_LOCK_TIMEOUT` через 5.8 с.

**Решение** (не проверено ни патчем, ни сценарием):
`fetch(url, { cache: 'no-store', headers: { Range } })` во всех запросах SW к CDN. SW и так
хранит данные сам, HTTP‑кэш ему не нужен.

### Мелкое

- **Первый визит идёт мимо SW:** `determineVideosDuration` ставит `src` основному
  `<video>` в обход `_waitForServiceWorker`. Решение — вызывать его после ожидания SW.
- **Ранний Play на медленном канале теряется** (замечено один раз): `checkCurrentVideo`
  заново ставит `src` после `durationchange`. Решение — запоминать намерение «играть» и
  применять его после смены `src`.

### Новое: лестница повторов слишком быстро уходит на паузу 30 с

**Что происходит** (код сайта от 27.10, сценарий `h1-outage-nosw`). CDN 5 с отвечает 503.
Первые перезагрузки идут через 0.5 и 1 с и сами попадают в окно отказа. Каждая такая
неудачная попытка считается **отдельной ошибкой**: за 4 с `errorCounter` дошёл до 6, а на
третьей ошибке ещё и запустилось обновление ссылок, которое тоже упало (code 4). Следующий
обычный сбой (через ~6 с после восстановления) уже попал на ступень «больше 5 ошибок» —
**пауза 30 с** (ошибка в +30.8 с, следующая попытка только в +62.8 с). Всё это
время плеер стоит в состоянии ошибки, нажатие Play не помогает. Счётчик сбросился бы только
после 30 с устойчивой игры, а их между сбоями не набралось.

| | старый код | код 27.10 |
|---|---|---|
| ошибки `<video>` | 4 | 6 |
| перезагрузки | 4 | 8 за минуту |
| простой | 0 с | 30 с |
| сыграно за 150 с | 144 с | 102 с |

**Почему.** `concatenate`, `onError`: `errorCounter++` на каждой ошибке, включая ошибки
самих попыток восстановления; пауза `5 < errorCounter ? 3e4 : min(4e3, 500·2^(n-1))`.

**Предлагаемое решение:**
1. **Считать «эпизод отказа», а не попытки.** Ошибка, случившаяся до того, как
   восстановление дало хоть какой‑то прогресс воспроизведения (новые `timeupdate` дальше
   `_lastGoodTime`), не увеличивает счётчик эпизодов — растёт только пауза внутри эпизода.
2. **Ступень 30 с — только после нескольких эпизодов** за, например, 5 минут, а не после
   шести попыток подряд.
3. **Разрешить пользователю прервать ожидание:** Play во время паузы восстановления
   запускает попытку сразу.

Эскиз (не проверен на стенде):

```js
// внутри onError, вместо безусловного errorCounter++
const progressed = player.currentTime() > plugin._episodeStartTime + 1;
if (!plugin._inEpisode || progressed) {
  plugin._inEpisode = true;
  plugin._episodeStartTime = plugin._lastGoodTime;
  plugin._episodes = (plugin._episodes || []).filter(t => Date.now() - t < 5 * 60e3);
  plugin._episodes.push(Date.now());
}
plugin._attempt = progressed ? 1 : (plugin._attempt || 0) + 1;
const delay = plugin._episodes.length > 3 ? 30000 : Math.min(4000, 500 * 2 ** (plugin._attempt - 1));
// ... и по 'playing' с прогрессом: plugin._inEpisode = false;
player.on('play', () => { if (plugin._recoveryTimer) { clearTimeout(plugin._recoveryTimer); plugin._retryRecovery(); } });
```

**Как проверить:** `h1-outage-nosw`, `h1-cut503-nosw`. Критерий: простой не больше, чем на
старом коде (0 с), при этом повторы ограничены по частоте.

## Как выкатывать

- **Версии.** По правилу из `sworker.js` поднять `swMain.js?v=N` и `/sworker.js?N`
  одновременно.
- **Канарейка.** Постепенно, через уже существующий `site.videoLoadingEngine`: сначала на
  часть пользователей.
- **Что смотреть в телеметрии:** `err` и `rb` из `videoTelemetry`; долю `brokenVideo` на
  1000 просмотров; долю `watched_partial`; распределение ступеней лестницы ретраев (H1).
  По этим цифрам видно, стало ли лучше на самом деле. Стенд проверяет только синтетику и
  Chrome.
- **Каждый фикс** прогнать теми же сценариями стенда:
  `node runner/run.mjs --patched=…`.
