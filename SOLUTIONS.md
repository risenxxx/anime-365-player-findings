# Предлагаемые решения (по коду сайта от 27.10.2026)

Только то, что осталось после исправлений на сайте. Что и как проверено — в
[REPORT.md](REPORT.md). Предложения к старой версии кода, большая часть которых уже
реализована, — в [archive/2026-10-25/SOLUTIONS.md](archive/2026-10-25/SOLUTIONS.md).

Код ниже — **эскизы**: на стенде они не прогонялись. Это направление, а не готовый код.
Перед выкаткой их стоит прогнать теми же сценариями (`node runner/run.mjs --patched=…`, см.
[patches/](patches/README.md)). Имена (`plugin`, `player`, `_lastGoodTime`, `_retryRecovery`)
соответствуют текущему `concatenate`: в минифицированной сборке это `m`, `v` и те же поля.

## R1. Лестница повторов слишком быстро уходит на паузу 30 с

**Проблема.** Короткий отказ CDN (5 с) без кэша SW: каждая неудачная попытка
восстановления внутри этого отказа увеличивает `errorCounter`. За 4 с он доходит до 6, и
следующий сбой ждёт 30 с, а Play не помогает. Было 0 с простоя, стало 30 с
([REPORT, R1](REPORT.md#r1-лестница-повторов-слишком-быстро-уходит-на-паузу-30-с-регрессия)).

**Решение:**
1. **Считать эпизоды отказа, а не попытки.** Ошибка, случившаяся раньше, чем восстановление
   дало хоть какой‑то прогресс воспроизведения (позиция ушла дальше точки, с которой
   восстанавливались), относится к тому же эпизоду: растёт только пауза внутри эпизода.
2. **Паузу 30 с включать по числу эпизодов за окно** (например, больше 3 за 5 минут), а не
   по числу попыток подряд.
3. **Play во время ожидания запускает попытку сразу**, а не через оставшуюся паузу.

```js
// в onError вместо безусловного errorCounter++
const progressed = player.currentTime() > (plugin._episodeFrom || 0) + 1;
if (!plugin._inEpisode || progressed) {
  plugin._inEpisode = true;
  plugin._episodeFrom = plugin._lastGoodTime;
  plugin._episodes = (plugin._episodes || []).filter(t => Date.now() - t < 5 * 60e3);
  plugin._episodes.push(Date.now());
  plugin._attempt = 0;
}
plugin._attempt++;
const delay = plugin._episodes.length > 3
  ? 30000
  : Math.min(4000, 500 * 2 ** (plugin._attempt - 1));

// эпизод закончился, когда воспроизведение пошло дальше точки восстановления
player.on('timeupdate', () => {
  if (plugin._inEpisode && player.currentTime() > plugin._episodeFrom + 1) plugin._inEpisode = false;
});
// пользователь не ждёт паузу до конца
player.on('play', () => {
  if (plugin._recoveryTimer && player.error()) {
    clearTimeout(plugin._recoveryTimer);
    plugin._retryRecovery();
  }
});
```

Ступени «свежие ссылки» и «альтернативный источник» при этом стоит привязать к номеру
попытки внутри эпизода (`_attempt`), а не к общему счётчику.

**Как проверить:** `h1-outage-nosw` (критерий: простой около 0 с, как на старом коде),
`h1-cut503-nosw`, `h1-long-outage-sw` (повторы по‑прежнему ограничены по частоте).

## H2. Битое место не перешагивается

**Проблема.** При порче байтов на CDN восстановление всегда идёт на `_lastGoodTime`, то есть
ровно в испорченное место, и ошибка декодирования повторяется 5–7 раз.

**Решение:** если ошибка декодирования повторилась в пределах ±1 с от предыдущей,
восстанавливаться на несколько секунд дальше (примерно один GOP, 2–5 с), с растущим шагом;
после нескольких шагов — `notifyBroken` и сообщение пользователю.

```js
// в onError, сразу ПОСЛЕ plugin._prepareRecovery(): он уже записал в player.lastSuccessTime
// позицию, куда restoreLastTime будет перематывать
if (err.code === 3) {
  const at = player.lastSuccessTime;
  if (Math.abs(at - (plugin._lastDecodeAt ?? -10)) < 1) {   // снова там же
    plugin._skip = Math.min((plugin._skip || 1) * 2, 30);   // 2 → 4 → 8 … с
    player.lastSuccessTime = at + plugin._skip;
  } else {
    plugin._skip = 0;
  }
  plugin._lastDecodeAt = at;
}
```

**Как проверить:** `h2b-decode-sw`, `h2a-no-sw-support` — после 1–2 ошибок проигрывание
продолжается за испорченным местом.

## H5. Сверка версии файла в кэше SW

**Проблема.** Кэш привязан к `m`, в метаданных нет версии файла. Если под тем же `m` на CDN
оказался другой файл, первое открытие смешивает старые куски с новыми и даёт ошибку
декодирования; только потом blacklist удаляет кэш.

**Решение:** хранить в метаданных валидатор (`ETag`, иначе `Last-Modified`; оба открыты в
`Access-Control-Expose-Headers` на проде) и раз за жизнь экземпляра SW сверять его перед
обслуживанием `m` из кэша; при расхождении размера или валидатора удалять кэш `m` до
первого ответа. Проверенная реализация для старого кода — патч
[archive/2026-10-25/patches/03](archive/2026-10-25/patches/03-h5-sw-cache-validation.md);
в v27 вызов удобно поставить рядом с `ensureMetadata` в fetch‑обработчике и делать через
`originFetch(url, { headers: { Range: 'bytes=0-0' } })`.

**Как проверить:** `h5-twin-sw` — 0 ошибок декодирования на всех открытиях.

## H8 без кэша SW: таймер плеера 30 с

**Проблема.** `_watchStall` ждёт 30 с без прогресса; в SW тайм‑аут чтения 15 с.

**Решение:** сократить таймер до 10–15 с, и/или срабатывать раньше, если буфер пуст
(`readyState < 3`) и сеть есть. Ложные срабатывания на медленном канале ограничены тем,
что таймер сбрасывается при любом прогрессе.

**Как проверить:** `h8-stall-nosw` — простой не больше 15 с.

## На заметку: о сетевых сбоях `notifyBroken` молчит

`notifyBroken()` теперь вызывается только после 3 ошибок декодирования. Если серверные
отчёты по `brokenVideo` используются для поиска проблемных серверов или файлов, имеет смысл
либо строить их по событиям `recovery_*` / `source_expired` из `videoTelemetry`, либо
вызывать `notifyBroken` и для долгих сетевых эпизодов (например, после 3 эпизодов R1 за 5
минут).

## Как выкатывать

- По правилу из `sworker.js` поднять `swMain.js?v=N` и `/sworker.js?N` одновременно.
- Постепенно, через `site.videoLoadingEngine`.
- Смотреть `err`, `rb` и события `recovery_*` в `videoTelemetry`, долю `brokenVideo`, долю
  `watched_partial`.
- Каждый фикс прогнать сценариями стенда (headless, без окон):
  `node runner/run.mjs --headless --patched=<набор> h1-outage-nosw h2b-decode-sw h5-twin-sw h8-stall-nosw`.
