# Отчёт: сбои воспроизведения веб‑плеера Anime 365

Доказательная база к [SOLUTIONS.md](SOLUTIONS.md) (предлагаемые решения) и
[README](README.md) (каталог проблем). Предмет — жалобы пользователей на бесконечные перезагрузки
проигрывания, прыжки в начало серии и обрывы потока. Каждая гипотеза проверялась
экспериментом. Ниже: где это в коде, как воспроизвести, что наблюдалось, патч и
результат с патчем. Если что‑то не воспроизвелось, так и написано, с объяснением, что именно
проверялось.

Код сайта — версии из [`vendor-manifest.json`](vendor-manifest.json), скачан 2026‑10‑24:
`videojs.concatenate.min.js?1789631056`, `embed.min.js?1785943069`, `sworker.js?24`,
`swMain.js?v=24`. Номера строк: для `swMain.js` — по оригиналу, для остальных — по выводу
`scripts/pretty.mjs` (`js-beautify -s 2`). Браузер — Google Chrome 155.0.8059.85, macOS.

`embed.min.js?1793007100`, `sworker.js?27` → `swMain.js?v=27` (манифест обновлён). Все

### Что изменилось в коде

- **`concatenate` (плеер):** переписано восстановление после ошибок. Позиция хранится
  отдельно (`_lastGoodTime`), все пути перезагрузки (включая blacklist) идут через общий

  в минуту), с 4‑й — один раз альтернативный источник; без сети или в скрытой вкладке
  попытки ждут. Сторожевой таймер: `waiting` дольше 30 с без прогресса → ошибка и
  восстановление. Реакция на `originStatus` (403/410) от SW. `notifyBroken` — только после
  3 ошибок декодирования; остальное — в телеметрию (`recovery_*`, `source_expired`).
- **`embed`:** одно сообщение `videoSettings` вместо двух; ответ на `requestVideoSettings`
  от SW; регистрация `sworker.js?27`.
- **`swMain.js` v27:** общий `originFetch` (до 3 попыток на 408/429/5xx и сетевые ошибки,
  тайм‑аут заголовков 15 с, `cache: 'no-store'`); `originReader` с тайм‑аутом чтения 15 с;
  при неудаче метаданных — прямой запрос и negative cache на 60 с вместо синтетического
  ответа; 416 за концом файла; настройки кэширования — по вкладке (`requestVideoSettings`);
  403/410 запоминаются и сообщаются вкладкам (`originStatus`); blacklist удаляет кэш `m`.
  Сверки версии файла (`ETag`/`Last-Modified`) нет.

### Изменения в стенде при этой проверке

- Сценарии `*-nosw` на новом коде проверяют «SW без кэша»: с v27 SW при выключенном
  кэшировании не пропускает запрос мимо себя, а проксирует его (`fetch(request)`).
  Контрольный сценарий принимает оба варианта.
- Детектор «сброс в начало» больше не срабатывает на 1–2 с `ct=0` при смене `src` с
  последующим восстановлением; новый детектор «перемотка не сработала». Старые прогоны
  пересчитаны (`runner/reanalyze.mjs`), их вердикты не изменились, кроме H3 (см. выше).
- Судья H6b считает запросы, обслуженные новым экземпляром SW (новый SW не пишет строку
  `Video caching disabled`).

## Как проверялось

- **Локальный стенд** ([README](README.md)): скачанный код сайта отдаётся с тех же путей
  (`server/site`), CDN — отдельный origin со сбоями (`server/cdn`), медиа синтетическое
  (H.264 High 1280×720, 1.6 Мбит/с, 1420 с, `moov` в начале). Chrome управляется по голому
  CDP, подключение только к странице: DevTools к воркеру не подключались ни разу (это
  отменяет его остановку по таймауту). Логи SW собираются тонкой обёрткой над
  `console.log`/`console.error` в `sworker.js`, логика `swMain.js` не меняется.
- **Живая проверка** (4.2): одна вкладка, обычный просмотр, звук выключен в плеере, NetLog
  без тел. В репозиторий попали только отредактированные выжимки
  ([`results/live-2026-10-24/`](results/live-2026-10-24/)). Сбои впрыскивались только в
  собственный трафик через локальный mitmproxy (`proxy/faults.py`).

### Поведение Chrome, которое определяет почти всё ниже

1. **Медиастек Chrome сам повторяет запрос после сетевого обрыва**, с той же позиции и с
   почти линейно растущей паузой (0.30, 0.36, 0.41 … 0.76 с …, порядка 30 попыток). Если же
   повтор получает HTTP‑ошибку (503), это для Chrome фатально:
   `PIPELINE_ERROR_READ`, code 2.
2. SW отвечает `206` **до того, как узнал статус CDN** (`respondWith` с потоком из
   `serve()`). Любой отказ CDN — 503, 403, обрыв — для браузера превращается в обрыв тела
   уже начатого ответа (`serve FAIL` → `controller.error()`), а такой обрыв Chrome
   повторяет. В итоге короткие отказы CDN с SW проходят незаметно (без SW те же отказы
   дают ошибку), а долгие растягиваются: 403 повторяется десятки раз, прежде чем плеер
   узнаёт об ошибке.

Поэтому многие сценарии без SW дают ошибку, а с SW нет. Это не значит, что соответствующий
код плеера верен: SW просто не даёт ошибке до него дойти.

## H1. Бесконечный цикл перезагрузок: `playing` обнуляет счётчик ошибок

**Код.** `videojs.concatenate.min.js:67-71`, `m.onError`: `v.errorCounter++`; если
`4 < errorCounter` — `notifyBroken()`, иначе `v.one("playing", () => v.errorCounter = 0)` и
через 500 мс `v.load()`. Если после каждой перезагрузки видео успевает заиграть, порог
недостижим. В ветке blacklist (`:57-62`) `errorCounter` тоже обнуляется.

**Как воспроизвести.** `node runner/run.mjs h1-cut503-nosw` — CDN 600 КБ/с, каждый ответ
обрывается после 6 МБ, первый запрос после обрыва получает 503; кэширование SW выключено
(`videoLoadingEngine: 'off'`).

**Наблюдение** ([h1-cut503-nosw](results/2026-10-25/h1-cut503-nosw.md)): за 150 с —
6 ошибок `code=2 PIPELINE_ERROR_READ`, после каждой `load()` и снова `playing`, позиция
восстанавливается. `notifyBroken` не вызван ни разу. Цикл идёт с периодом ~30 с и не
кончится, пока не перестанет сбоить CDN.

С SW (`h1-cut503-sw`, `h1-outage-sw` — 5 с отказа) ошибок нет: их поглощают повторы
Chrome, см. «Поведение Chrome». С 40‑секундными отказами (`h1-long-outage-sw`) — 4 ошибки
и 86 с остановок без `notifyBroken`, механизм тот же. `h1-outage-nosw` (5 с отказа без
SW) дал 4 ошибки в официальном прогоне и 5 в предварительном. Обрывы без HTTP‑ошибок
(`h1-cut-*`) не видны ни с SW, ни без: соединение переоткрывает `serve()` или сам Chrome.

**Патч 01.** Ошибки считаются в скользящем окне 2 минуты, без сброса по `playing`.
Пятая ошибка за 2 минуты → `notifyBroken`. Паузы между перезагрузками растут:
0.5 → 1 → 2 → 4 с.

**С патчем** ([h1-cut503-nosw](results/2026-10-25-patched/h1-cut503-nosw.md)): 5 ошибок,
4 перезагрузки, затем `notifyBroken` (вызван 1 раз; без патча — 0 при 6 ошибках). Цикл
ограничен и сайт узнаёт о поломке. **Оборотная сторона:** после пятой ошибки плеер
сдаётся и стоит — сыграно 112 с против 142 с без патча, где бесконечные перезагрузки
каждый раз снова запускали видео. Вывод: окно ошибок нужно, но после `notifyBroken` стоит
не останавливаться, а перейти на альтернативные источники и продолжать попытки с длинной
паузой (в патче этого нет). `h1-outage-nosw` — без изменений (3 ошибки раз в ~30 с, ниже
порога). `h1-long-outage-sw` — ошибок `<video>` нет (патч 02 пережидает отказ повторами),
но остановки те же (87 с против 86 с): 40 с CDN недоступен, играть нечего.

## H2. Прыжок в начало серии после ошибки

### H2a. Позиция `0` залипает после ошибки на старте

**Код.** `concatenate:67`: `lastSuccessTime` пишется, только если он `null`; `:72-74`
`restoreLastTime` обнуляет его в `null`, только если `0 < lastSuccessTime`. Первая ошибка
ровно при `ct = 0` оставляет `0` навсегда, следующая ошибка позицию не восстанавливает.

**Как воспроизвести.** `node runner/run.mjs h2a-no-sw-support`: регистрация SW не удаётся
(`/sworker.js` → 404), первый медиазапрос → 503, затем в середине серии ошибка
декодирования (байты 40–41 МБ занулены).

**Наблюдение** ([h2a-no-sw-support](results/2026-10-25/h2a-no-sw-support.md)): code 4 при
`ct = 0` → `lastSuccessTime = 0`; на 189 с code 3 → `load()` без восстановления → позиция
`0:00`, плеер на паузе.

Это происходит, только когда страницей **не управляет SW**: при первом визите до
регистрации, при неудачной регистрации, в браузерах без SW. С контроллером SW code 3/4 уходит
в ветку blacklist (H2b), а ошибка сети во время preload приходит в Chrome только по Play,
когда `ct` уже ~0.008 > 0 (`h2a-zero-*`, `h2a-preload-nosw` — не воспроизводится,
позиция восстанавливается).

### H2b. Ветка blacklist не восстанавливает позицию

**Код.** `concatenate:53-62`: при code 3/4 и наличии контроллера SW — blacklist `m`,
`postMessage({type:'blacklist'})`, `v.src(currentSrc + "&rand=…")`, `v.load()` и
`return` до регистрации `canplay → restoreLastTime`.

**Как воспроизвести.** `node runner/run.mjs h2b-decode-sw`: байты 40–41 МБ занулены,
перемотка на 2:50.

**Наблюдение** ([h2b-decode-sw](results/2026-10-25/h2b-decode-sw.md)): на 189 с
`PIPELINE_ERROR_DECODE` → `MEDIA_ERR_DECODE: Blacklisting mParam … retrying immediately`
→ позиция `189 → 0`, пауза.

**Патч 01** (общий с H1). Последняя хорошая позиция хранится отдельно от флага «нужно
восстановить» и обновляется по `timeupdate`. `0` её не затирает. Ветка blacklist тоже
вешает `canplay → restoreLastTime`.

**С патчем** ([h2a-no-sw-support](results/2026-10-25-patched/h2a-no-sw-support.md),
[h2b-decode-sw](results/2026-10-25-patched/h2b-decode-sw.md)): сброса в 0:00 нет, позиция
восстанавливается на 3:09. Но в этих сценариях байты на 3:09 испорчены на самом CDN,
поэтому восстановление ведёт на то же место → снова ошибка декодирования (4–6 раз) →
`notifyBroken`. Если же испорчен только кэш SW (как в H5), обход SW после blacklist эту
ошибку снимает. Для порчи на CDN нужна ещё одна доработка: при повторной ошибке
декодирования на той же позиции восстанавливаться на несколько секунд дальше.

## H3. Неудача метаданных → синтетический `206 …/*` вместо прямого запроса

**Код.** `swMain.js:1660-1695` `_ensureMeta` ловит любое исключение (`meta/open THREW`,
`probe NOT OK`) и возвращает `null`. Fetch‑обработчик `:2640-2737` откатывается на
`fetch(request)` только при исключении, а при `null` отвечает `206` с
`Content-Range: bytes 0-104857600/*` и `Content-Length: 104857601`. Запасной конец
`1024*1024*100` на единицу больше 100 МБ (`:2645`, `:2658`).

**Как воспроизвести.** `node runner/run.mjs h3-first-503-sw` (первые 2 запроса → 503) и
`h3-hidden-range-sw` (CDN не открывает `Content-Range` в `Access-Control-Expose-Headers`).

**Наблюдение.**
- [h3-first-503-sw](results/2026-10-25/h3-first-503-sw.md): `browser req … end= 104857600
  total= MISSING`; дальше `serve()` открыл соединение со следующей попытки.
  **Уточнение от 27.10:** первоначальный вывод «видимых последствий нет» был неверным.
  Детекторы стенда не проверяли, что перемотка действительно сработала. После ответа с
  неизвестным размером (`/*`) перемотка на 11:40 дала запрос с байта 950 272 (сразу за
  `moov`), и видео пошло **с начала** (позиция 1.4 → 2.4 → 3.4 с); перемотка на 5:00 — то же.
  То есть один отказ CDN на старте ломает перемотку на весь сеанс. Новый детектор
  «перемотка не сработала» находит это в старом прогоне; с патчем 02 и на коде сайта от
  27.10 перемотки работают.
- [h3-hidden-range-sw](results/2026-10-25/h3-hidden-range-sw.md): `origin BAD range …
  missing Content-Range` → синтетический ответ → ошибка code 4 на старте → blacklist →
  дальше мимо SW. Пользователь видит короткую ошибку на старте, кэширования для этого
  видео в сессии нет.
- **На проде** CDN сейчас открывает `content-range, content-type, content-length,
  cache-control, accept-ranges, date, etag, last-modified, x-cache, x-content-length,
  x-server-id, x-uid` (живая запись), так что второй случай на проде не встречается. Он
  станет актуален, если какой‑то сервер или CDN отдаст ответ без этого заголовка.

**Патч 02.** Если размер получить не удалось, `return fetch(request)`: браузер получает
настоящий ответ CDN, как без SW.

**С патчем** ([h3-first-503-sw](results/2026-10-25-patched/h3-first-503-sw.md),
[h3-hidden-range-sw](results/2026-10-25-patched/h3-hidden-range-sw.md)): синтетического
ответа больше нет. Первая версия патча сразу отдавала `fetch(request)`, и **это была
регрессия**: браузер получал настоящий 503, а он для медиастека Chrome фатален (code 4 на
старте, хотя без патча короткий 503 был незаметен). Текущая версия сначала дважды
повторяет получение метаданных (через 0.5 и 1 с) и только потом отдаёт прямой запрос. Итог:
- 503 на старте: ошибок нет, но старт на ~4 с дольше (без патча — 0 с);
- `Content-Range` не открыт: ошибки code 4 на старте нет (2 с остановки), но каждый запрос
  заново тратит ~1.5 с на повторы. Доработка: после первой неудачи запоминать для `m`, что
  метаданных нет, и сразу отдавать прямой запрос.

## H4. Неудачное переоткрытие соединения рвёт поток; истёкшая подпись

**Код.** `swMain.js:1862-2167` `serve()`. После смерти соединения (`origin read DIED
mid-serve`) внешний цикл переоткрывает его через `_openConnection` (`:1771-1795`),
сколько угодно раз, но **первая же неудачная попытка** (`origin fetch NOT OK`) бросает
исключение → `serve FAIL` → `controller.error()` (`:2143-2154`). На 403 SW никак не
сигнализирует странице; `_refreshSources` (`concatenate:335-352`) вызывается только по
таймеру раз в 23 ч (`:353-355`).

**Как воспроизвести.** `node runner/run.mjs h4-expired-403-sw`: на 45‑й секунде все
открытые ответы обрываются, все запросы со старой подписью (`sig=1`) получают 403;
`/translations/sources/<id>` выдаёт свежую.

**Наблюдение** ([h4-expired-403-sw](results/2026-10-25/h4-expired-403-sw.md)): 149
`serve FAIL` подряд; Chrome повторяет каждый (см. «Поведение Chrome»), пока не кончится
буфер и закэшированный участок; первая ошибка `<video>` — примерно через 85 с, дальше
каждая `load()` даёт ещё ~30 с ожидания и снова ошибку. За 200 с — 4 ошибки, 119 с
остановок, **353 запроса к CDN с просроченной подписью**, ни одного запроса `/sources/`.

**Патчи.** 02 — до 4 повторов переоткрытия с паузой 0.5–4 с для 5xx/429/сети (не для
403). 04 — SW сообщает странице `{type:'originStatus', status:403}`. 05 — плеер по нему
вызывает `_refreshSources()` и переключает `src` на свежую ссылку с сохранением позиции.

**С патчем** ([h4-expired-403-sw](results/2026-10-25-patched/h4-expired-403-sw.md)): ошибок
`<video>` нет, остановок нет, сыграно 244 с из 245 (без патча — 121 с, 119 с остановок).
Плеер получил `originStatus 403`, запросил `/sources/` и один раз переключил `src` на свежую
ссылку.

## H5. Битый кэш живёт сутки, blacklist забывается

**Код.** Кэш привязан только к `m` (`swMain.js:31-33`, `:100-102`), метаданные — размер и
тип (`:306-325`), без ETag/Last-Modified и хоста. Сообщение `blacklist` (`:2827-2852`)
останавливает загрузчик, но кэш `m` не удаляет. Blacklist — только в памяти страницы
(`concatenate:6`) и SW (`swMain.js:46`).

**Как воспроизвести.** `node runner/run.mjs h5-twin-sw`: открытие 1 — файл A, 40 с игры;
затем CDN под тем же URL отдаёт B (другая кодировка, дополнена до того же размера);
пауза 45 с, открытия 2 и 3 с перемоткой на 6:00.

**Наблюдение** ([h5-twin-sw](results/2026-10-25/h5-twin-sw.md)): при **каждом** новом
открытии — `PIPELINE_ERROR_DECODE` на 6:00 → blacklist → позиция `360 → 0`. Кэш
`video-cache-v1-<m>` после blacklist на месте. На проде то же случится при перекодировании
файла или при альтернативном источнике с тем же `m` и другими байтами.

**Патч 03.** В метаданных хранится валидатор (`ETag`, иначе `Last-Modified`; оба на проде
открыты в `Expose-Headers`). Раз за жизнь экземпляра SW закэшированный `m` сверяется с CDN
(`Range: bytes=0-0`), при расхождении размера или валидатора кэш `m` удаляется.
Сообщение `blacklist` удаляет кэш `m`.

**С патчем** ([h5-twin-sw](results/2026-10-25-patched/h5-twin-sw.md)): ошибок декодирования
нет, сбросов в начало нет (без патча — 2 и 2). При повторном открытии SW сверил валидатор,
увидел другой `Last-Modified` и удалил кэш `m`.

### H6b. Перезапущенный SW молча выключает кэширование — воспроизведено

Найдено на живом сайте: пауза началась на +196 с, воркер был остановлен на +240.9 с
(~45 с простоя, когда у него не было открытых соединений с CDN — серия уже вся в кэше) и
запущен снова на +385.6 с. После продолжения запрос пошёл мимо SW, и **53 МБ были скачаны
из сети при полностью заполненном кэше**.

**Код.** `swMain.js:50` `videoCachingEnabled = false` и `:65` `videoMode = 'multithread'` —
только в памяти. Страница шлёт `setVideoCachingEnabled`/`setVideoMode` только при загрузке
и `controllerchange` (`embed.min.js:19-33`). Новый экземпляр SW обходит кэш
(`swMain.js:2630-2633`) до перезагрузки страницы.

**Как воспроизвести.** `node runner/run.mjs h6b-sw-restart` (остановка воркера командой
`ServiceWorker.stopAllWorkers` с сессии страницы, так же как при простое).
[Результат](results/2026-10-25/h6b-sw-restart.md): второй экземпляр, запросы мимо SW
(`Video caching disabled, bypassing SW`), кэш SW не используется.

**Патч 07.** Выбранный страницей режим сохраняется в Cache Storage, новый экземпляр
восстанавливает его до обработки первого запроса.

**С патчем** ([h6b-sw-restart](results/2026-10-25-patched/h6b-sw-restart.md)): второй
экземпляр пишет `restored video settings: caching= true mode= singlethread`, запросов мимо SW
нет (без патча — 2), ошибок и остановок нет.

## H8. Зависший поток CDN: нет таймаута чтения — воспроизведено

Найдено на живом CDN при впрыске сбоев через mitmproxy: обрыв, сделанный посреди
HTTP/2‑потока, превратился в «зависший» поток — байты не идут, поток не сброшен. Плеер
стоял 42 с и 31 с без единой ошибки, пока сценарий не сделал далёкую перемотку
([proxy.md](results/live-2026-10-24/proxy.md),
[netlog-proxy.md](results/live-2026-10-24/netlog-proxy.md)).

**Код.** `swMain.js:2056` `await conn.reader.read()` и `:1950` в `idleDrain` — без
таймаута; загрузчик ждёт `_foregroundFetches == 0` (`:2232-2234`), то есть стоит вместе с
`serve()`.

**Как воспроизвести.** `node runner/run.mjs h8-stall-sw h8-stall-nosw`: первый медиаответ
после 6 МБ перестаёт отдавать байты, соединение остаётся открытым; через 100 с «пользователь»
перематывает на +5 с.

**Наблюдение** ([h8-stall-sw](results/2026-10-25/h8-stall-sw.md),
[h8-stall-nosw](results/2026-10-25/h8-stall-nosw.md)): и с SW, и без SW — 114 с остановки,
ошибок нет, к CDN за всё время **один** запрос. Перемотка на +5 с не помогает: позиция
внутри уже запрошенного диапазона, и ждут то же соединение. Без SW это поведение самого
Chrome. С SW это можно исправить.

**Патч 06.** Таймаут чтения в `serve()`: 12 с без байтов от CDN → соединение обрывается и
переоткрывается с той же позиции (вместе с патчем 02 — с повторами).

**С патчем** ([h8-stall-sw](results/2026-10-25-patched/h8-stall-sw.md)): 0 с остановок
(без патча — 114 с), сыграно 138 с. `origin read STALLED 12000 ms` → переоткрытие с той же
позиции. Без SW ([h8-stall-nosw](results/2026-10-25-patched/h8-stall-nosw.md)) без изменений
(114 с): это поведение самого Chrome, исправить можно только в SW или в плеере (сторожевой

## Второстепенное

- **Первый визит идёт мимо SW.** `determineVideosDuration` (`concatenate:386-398`) в
  ветке `isOneVideo` ставит `src` основному `<video>` и вызывает `load()` в обход
  `_waitForServiceWorker` (`:405-411`). При первом визите элемент открывает прямое
  соединение с CDN до того, как SW возьмёт управление. Без последствий для
  пользователя, но первый просмотр не кэшируется так, как задумано.
- **Соединения на перемотку** (живой CDN через прокси, HTTP/2): 2–4 запроса к CDN на одну
  перемотку. На прямом соединении после заполнения кэша — 0.
- **`ERR_CACHE_LOCK_TIMEOUT`** на живом CDN: второй параллельный range‑запрос SW к тому же
  URL ждал блокировку записи HTTP‑кэша Chrome и упал через 5.8 с. SW к тому же дублирует
  серию в HTTP‑кэш (в тестовом профиле — 249 МБ). Предложение:
  `fetch(url, { cache: 'no-store', headers: { Range } })` в SW. Не проверено патчем.
- **Альтернативные источники работают.** При ошибках сертификата на основном CDN (из‑за
  ошибки в драйвере стенда) плеер перешёл на `data-alternative-sources` (другой хост) и
  доиграл без видимых проблем.
- **Ранний Play на медленном канале теряется** (замечено один раз при 300 КБ/с): после
  `durationchange` `checkCurrentVideo` заново ставит `src` и вызывает `load()`, плеер
  остаётся на паузе в 0:00. Отдельным сценарием не проверялось.
- **`parseRange`** (`swMain.js:110-118`) не понимает `bytes=-N`, на диапазон за концом файла
  нет 416. Браузер такие запросы для `<video>` не шлёт, проверено только чтением кода.
- **`initWaitUntilEmbedAvailable`** (`embed.min.js:119-138`) делает `location.reload()` в
  iframe, как только `isAvailable` вернёт true. Если сервер и отрисовка embed разойдутся,
  получится перезагрузка каждые 10 с. Сейчас маловероятно (embed `no-store`), не проверялось.

## Живая проверка (4.2)

Одна серия, вход в аккаунт, одна вкладка. Сценарий ~10 мин: старт, 60 с, перемотки
на 7:00 / 15:00 / 3:00 по 45 с, пауза 330 с, продолжение 90 с.

**Параметры файла** ([media-params.json](results/live-2026-10-24/media-params.json),
только числа): 644 492 800 байт, 1420.033 с (~3.6 Мбит/с), 1920×1080, H.264 Main@4.0, `moov` в
начале, `Accept-Ranges: bytes`. Синтетический файл стенда легче (1280×720 High, 1.6 Мбит/с).
`make-media.sh` принимает параметры из окружения, если нужен двойник ближе к проду.

**Без прокси** ([baseline.md](results/live-2026-10-24/baseline.md),
[netlog-baseline.md](results/live-2026-10-24/netlog-baseline.md)): CDN по HTTP/3,
загрузчик SW скачал 525 МБ за 22.6 с, перемотки из кэша. Ошибок, сбросов позиции и остановок
нет. Воркер остановлен в паузе и перезапущен — это H6b.

**Через прокси со сбоями** ([proxy.md](results/live-2026-10-24/proxy.md)): прокси
переводит транспорт на HTTP/2 (QUIC выключен), так что транспортное поведение берётся только
из записи без прокси. 2 обрыва по 8 МБ превратились в зависания по 42 и 31 с — это H8.

Замечания к методике (стенд, не сайт):
- профиль Chrome, который хоть раз открыл сайт напрямую, после открытия через mitmproxy
  с подменой сертификата страницы получал `InvalidStateError` от API SW; поэтому прокси
  вскрывает только хосты CDN;
- обёртки прототипов `HTMLMediaElement`/`Element` в инструментовке на настоящем сайте
  ломали API SW в iframe embed при повторном визите; живые прогоны используют облегчённую
  инструментовку (только события и позиция).
