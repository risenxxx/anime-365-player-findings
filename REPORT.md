## Что осталось

### R1. Лестница повторов слишком быстро уходит на паузу 30 с (регрессия)

**Где:** `concatenate`, `onError` (строки 76-92), `_retryRecovery` (63-73). На каждой ошибке
`errorCounter++` (79); пауза перед следующей попыткой
`5 < errorCounter ? 3e4 : min(4e3, 500·2^(n-1))` (90); счётчик обнуляется только после 30 с
устойчивой игры (12).

**Как воспроизвести:** `node runner/run.mjs --headless h1-outage-nosw` — CDN 600 КБ/с,
каждый ответ обрывается после 6 МБ, следующие 5 с CDN отвечает 503; кэш SW не используется
(так бывает при первом визите, в браузерах без SW, в режиме без кэширования).

**Наблюдение** ([h1-outage-nosw](results/2026-10-27/h1-outage-nosw.md)):

```
+11.6s error ct=8.18 code=2            ← обрыв + 503
+12.1s load → playing ct=8.18
+12.9s error ct=8.85 code=2            ← попытка попала в окно отказа
+13.8s error ct=8.85 code=2            ← ещё одна
+15.4s src= (свежие ссылки) → error code=4, src=&rand → error code=4
+25.0s playing ct=8.86                 ← восстановилось через ~13 с
+30.8s error ct=14.61 code=2           ← следующий обрыв: errorCounter уже 6
                                          → пауза 30 с, плеер стоит, Play не помогает
+62.8s load → playing ct=14.61
```

| | старый код | код 27.10 |
|---|---|---|
| ошибки `<video>` | 4 | 6 |
| перезагрузки | 4 | 8 за минуту |
| простой | **0 с** | **30 с** |
| сыграно за 150 с | 144 с | 102 с |

Причина: каждая неудачная попытка восстановления внутри одного 5‑секундного отказа
считается отдельной ошибкой. За 4 с счётчик доходит до 6, а 30 с устойчивой игры, которые
бы его сбросили, между сбоями не набираются. С кэшем SW тот же отказ незаметен
(`h1-outage-sw`: 0 ошибок): его поглощают повторы в SW и медиастеке Chrome.

### H2. Битое место не перешагивается

**Где:** `concatenate`, `_prepareRecovery` (13-15) и `restoreLastTime` (105-107):
восстановление всегда идёт на `_lastGoodTime`, то есть ровно туда, где сломалось.

**Наблюдение:** байты 40–41 МБ на CDN занулены, ошибка декодирования на 3:09.
- [h2b-decode-sw](results/2026-10-27/h2b-decode-sw.md): 7 ошибок code 3, 8 перезагрузок за
  минуту, 20 с простоя, `notifyBroken` после третьей;
- [h2a-no-sw-support](results/2026-10-27/h2a-no-sw-support.md) (без контроллера SW): 5 ошибок
  code 3 на том же месте.

В начало серия больше не уходит, но дальше испорченного места проигрывание не идёт.

### H5. Нет сверки версии файла в кэше SW

**Где:** `swMain.js`, `saveMetadata` (431-449): в метаданных кэша только `totalSize` и
`contentType`. Кэш привязан к `m`; blacklist (3030-…) теперь удаляет кэш `m`.

**Наблюдение** ([h5-twin-sw](results/2026-10-27/h5-twin-sw.md)): под тем же `m` на CDN другой
файл той же длины. Первое открытие после подмены — 1 ошибка декодирования (куски из кэша
смешались с новыми байтами), затем blacklist удаляет кэш, и следующие открытия чистые.
Раньше ошибка и прыжок в начало были при каждом открытии.

### H8 без кэша SW: таймер плеера 30 с

**Где:** `concatenate`, `_watchStall` (93-100): `waiting` без прогресса дольше 30 с → ошибка
и восстановление. В SW тайм‑аут чтения — 15 с (`originReader`, 157-180).

**Наблюдение** ([h8-stall-nosw](results/2026-10-27/h8-stall-nosw.md)): CDN перестаёт отдавать
байты, не закрывая соединение. Простой 30 с (раньше 114 с); с кэшем SW — 0 с
([h8-stall-sw](results/2026-10-27/h8-stall-sw.md)).

### На заметку: `notifyBroken` только для ошибок декодирования

`notifyBroken()` теперь вызывается после 3 ошибок декодирования; сетевые сбои уходят в
`videoTelemetry` (`recovery_reload`, `recovery_refresh`, `recovery_alternative`,
`recovery_stall`, `source_expired`). Если отчёты по `brokenVideo` используются на сервере,
сетевые проблемы в них больше не попадают.

- **H6b:** воркер перезапускался во время паузы, но после продолжения из сети не ушло ни

## Поправка к исходному отчёту

В отчёте от 25.10 по H3 было «механизм подтверждён, видимых последствий нет». Это было
неверно: стенд не проверял, что перемотка действительно сработала. На старом коде после
ответа с неизвестным размером (`/*`) перемотка на 11:40 запросила данные с байта 950 272 (сразу
за `moov`), и видео пошло с начала; перемотка на 5:00 — то же. Новый детектор «перемотка не
сработала» находит это в старых прогонах; при пересчёте (`runner/reanalyze.mjs`) из 48
вердиктов архивных прогонов изменился только этот.

## Как проверялось

- **Локальный стенд** ([README](README.md#как-запустить-локальный-стенд)): скачанный код сайта
  по манифесту с sha256, локальный CDN со сбоями на отдельном origin, синтетическое видео,
  настоящий Chrome по CDP (только страница, DevTools к воркеру не подключаются), headless.
- **Живая проверка:** обычный просмотр одной серии в одной вкладке, NetLog без тел; в
  репозитории только отредактированные выжимки.
- **Важное поведение Chrome:** медиастек сам повторяет запрос после сетевого обрыва (~30
  попыток с растущей паузой), но HTTP‑ошибку на повторе считает фатальной. Через SW любой
  отказ CDN выглядит для браузера как обрыв, поэтому с кэшем SW короткие сбои незаметны, а
  без него те же сбои доходят до плеера.
- **Сценарии `*-nosw`** на коде v27 проверяют «SW без кэша»: при выключенном кэшировании SW
  проксирует запрос (`fetch(request)`), а не пропускает его мимо себя.

### Safari

Не автоматизировался. Ручной чек‑лист: Разработка → Service Workers → домен сайта — есть
`/sworker.js?27`; консоль iframe embed — `Error #N`, `recovery_*`; две перемотки в середину —
позиция не уходит в 0:00; пауза 6 минут **с закрытым инспектором воркера**, затем Play — нет
повторной закачки и ошибки; 8 минут непрерывно — нет остановки около 5‑й минуты.

### Ограничения

Локальный CDN — HTTP/1.1 (прод — HTTP/3); субтитры в локальной сборке выключены; выводы о
браузере — для Chrome 155 на macOS; синтетическое видео легче настоящего (1.6 против
~3.6 Мбит/с).
