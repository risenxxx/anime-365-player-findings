# Патчи

> **Архив.** Патчи 01–07 написаны и проверены против старой версии кода (`concatenate?1789631056`, `swMain.js?v=24`). К коду сайта от 27.10 они не применяются; большая часть их идей на сайте уже реализована.

Диффы против кода из `vendor-manifest.json`: `js/**` в разметке `scripts/pretty.mjs`
(`js-beautify -s 2`), `swMain.js` против оригинала (он не минифицирован). Применяются по
порядку номеров, каждый поверх предыдущих: `node scripts/apply-patches.mjs all` →
`vendor/patched/all/`. Прогон с патчами: `node runner/run.mjs --patched=all`.

Патчи минимальные: они показывают направление исправления и проверяются теми же
сценариями. Это не готовый код для прода. Пороги (12 с, 2 мин, 4 попытки) выбраны для стенда.

**У каждого патча два файла:**
- `NN-….md` — читаемая версия для переноса в исходник: где искать код (в том числе по
  строкам логов, которые переживают минификацию), «было» и «стало» в читаемом JS,
  инварианты, проверка и результат, что патч не решает. Комментарии в коде этих файлов
  переведены на русский.
- `NN-….patch` — точный дифф, на котором прогонялся стенд (`--patched`). Для
  `concatenate` он наложен на prettified‑копию минифицированного файла, поэтому к исходнику
  сайта напрямую не применится.

## Перенос в исходники

- **01, 05 (`videojs.concatenate`).** Правки в `onError`, `restoreLastTime`, обработчике
  `message` от SW и `_refreshSources` (там добавлен необязательный колбэк). В исходнике
  это те же функции плагина `concatenatePlugin`. `v.lastSuccessTime` можно переименовать
  (например, в `lastGoodTime`) и завести явный `restorePending`. Новое поведение: Play
  после восстановления вызывается только при `restorePending`.
- **02–04, 06, 07 (`swMain.js`).** Файл не минифицирован, диффы переносятся как есть.
  Затем по правилу из `sworker.js` нужно поднять `swMain.js?v=N` и `/sworker.js?N` в
  `embed.js`/`main.js`. Патч 03 при первом запуске сбросит кэши, записанные без валидатора.
  Это разовая потеря кэша, а не ошибка.

## Что патчи пока не решают

Видно в прогонах с патчами (`results/2026-10-25-patched/`):
- **01:** после `notifyBroken` плеер стоит. Лучше перейти на альтернативные источники и
  продолжать попытки с длинной паузой.
- **01:** если байты испорчены на самом CDN, восстановление позиции ведёт на то же место,
  и ошибка повторяется. При повторной ошибке декодирования на той же позиции стоит
  восстанавливаться на несколько секунд дальше.
- **02:** если `Content-Range` недоступен постоянно, каждый запрос тратит ~1.5 с на повторы.
  Стоит запоминать для `m`, что метаданных нет.
- **06** работает только с SW. Без SW (у Chrome нет своего таймаута) нужен сторожевой
  таймер в плеере на долгий `waiting`.

## Проверено, патча нет

- H6 (остановка SW на 5‑й минуте долгого fetch‑события) и H7 (новая версия SW рвёт
  просмотр) в Chrome 155 не воспроизводятся, см. REPORT.md. Патчей к ним нет.
- `fetch(..., { cache: 'no-store' })` для запросов SW к CDN (двойное хранение в HTTP‑кэше,
  `ERR_CACHE_LOCK_TIMEOUT` на живом CDN) только предложен, сценария и патча нет.
